# القرارات المعمارية — وُصلة

## ADR-001 — تيليجرام كواجهة أساسية
**القرار:** تيليجرام هو واجهة المستخدم الأساسية للمنصة (14 بوتاً)، وليس تطبيق جوال.
**السبب:** انتشار واسع في السوق السعودي، لا حاجة للتثبيت، إشعارات فورية مدمجة، تكلفة تطوير أقل.
**البدائل:** React Native، Flutter، PWA.
**الأثر:** سرعة الوصول للسوق، قيود على التخصيص البصري.

## ADR-002 — TypeScript + Bun كمنصة تطوير
**القرار:** TypeScript مع Bun runtime.
**السبب:** تحليل المشاريع المرفقة أظهر أن TypeScript هو الأكثر استخداماً في المشاريع الناضجة (Nona, Vees, Tooru). Bun يوفر سرعة تشغيل أعلى من Node.js.
**البدائل:** Python (مشروع ODD)، PHP (Vees-2).
**الأثر:** توحيد اللغة عبر كل مكونات المنصة.

## ADR-003 — نموذج معماري هجين
**القرار:** Modular Monolith للخدمات الأساسية + Microservices للخدمات الحرجة.
**السبب:** تجنب تعقيد Microservices الكامل من اليوم الأول، مع الحفاظ على قابلية فصل الخدمات عالية الحمل (محرك التوزيع، الدفع، الإشعارات).
**البدائل:** Microservices كامل، Monolith كامل.
**الأثر:** توازن بين التعقيد التشغيلي وقابلية التوسع.

## ADR-004 — Supabase PostgreSQL كمصدر وحيد للحقيقة
**القرار:** PostgreSQL عبر Supabase هو المصدر الوحيد للبيانات الدائمة.
**السبب:** Atomic transactions، Row-Level Security، Realtime subscriptions.
**البدائل:** MongoDB، MySQL، DynamoDB.
**الأثر:** حلول مضمونة لمشاكل race condition (مثل double-accept).

## ADR-005 — Atomic SQL RPCs للعمليات الحرجة
**القرار:** استخدام Stored Procedures مع row-level locking للعمليات الذرية (قبول الطلب، الإلغاء).
**السبب:** منع حالات السباق (race conditions) في بيئة متعددة الخيوط.
**المستوحى من:** tooru (ADR-001) + Koolex test plan.
**الأثر:** أمان تام من double-accept.

## ADR-006 — نموذج اشتراك ثابت (0% عمولة)
**القرار:** إيراد المنصة من الاشتراكات فقط، لا عمولة على الطلبات.
**السبب:** زيادة رضا السائقين وتقليل معدل الدوران.
**الأسعار:** مشاوير 250 ريال، توصيل 250 ريال، مزدوج 400 ريال، شهر مجاني أول.
**الأثر:** نموذج تجاري واضح وجاذب للسائقين.

## ADR-007 — قفل الطلب النشط في قاعدة البيانات
**القرار:** `active_ride_id` على جدول `drivers` مع UNIQUE constraint.
**السبب:** سائق واحد ← طلب نشط واحد. يُضبط ويُفرَّغ في معاملات ذرية.
**الأثر:** منع استقبال طلبين لنفس السائق.

## ADR-008 — خريطة سياقات (Bounded Context Map)
**القرار:** تقسيم المجال إلى سياقات محددة: Transport (Core)، Dispatch (Core)، Identity (Supporting)، Financial (Supporting)، Geo (Generic).
**السبب:** فصل المسؤوليات ووضوح الحدود بين المكونات.
**الأثر:** سهولة الصيانة والتوسع.

## ADR-009 — Event-Driven للخدمات غير المتزامنة
**القرار:** استخدام Event Bus (Kafka/NATS في الإنتاج، InMemory في التطوير) للأحداث غير المتزامنة.
**الأحداث:** `ride.requested`, `driver.matched`, `payment.completed`, `subscription.expiring`.
**الأثر:** فصل الخدمات، قابلية التوسع الأفقي.

## ADR-010 — Polyglot Persistence
**القرار:** استخدام قاعدة البيانات المناسبة لكل خدمة.
- PostgreSQL: البيانات العلائقية
- Redis: كاش + مواقع لحظية
- Elasticsearch: بحث
- S3: ملفات وصور
- Neo4j (مستقبلاً): كشف الاحتيال
**الأثر:** أداء أمثل لكل حالة استخدام.

## ADR-011 — دعم متعدد المستأجرين (Multi-Tenancy)
**القرار:** ثلاثة نماذج عزل (Pool, Bridge, Silo) حسب حجم العميل المؤسسي.
**السبب:** دعم المؤسسات الصغيرة والمتوسطة والكبيرة بنماذج عزل مختلفة.
**الأثر:** مرونة في استيعاب مختلف أنواع العملاء.

## ADR-012 — فصل الأسرار عن الكود
**القرار:** جميع الأسرار من متغيرات البيئة. `.env.example` يحتوي أسماء المتغيرات فقط.
**السبب:** أمان المعلومات ومنع تسرب الأسرار.
**الأثر:** CI/CD آمن، نشر متعدد البيئات.

## ADR-013 — Clean Architecture (Domain → Application → Infrastructure)
**القرار:** فصل صارم بين Domain (قواعد العمل)، Application (حالات الاستخدام)، Infrastructure (التكاملات).
**السبب:** اختبارability، قابلية الصيانة، استقلالية المجال عن التقنيات.
**الأثر:** كود نظيف، قابل للاختبار، مستقل عن البنية التحتية.

## ADR-014 — آلة حالة صارمة للرحلات
**القرار:** جميع انتقالات حالة الرحلة محكومة بجدول انتقالات (FSM) في قاعدة البيانات ومنطق التطبيق.
**الحالات:** requested → dispatching → matched → arrived → started → finished
**الأثر:** منع أي انتقال غير قانوني، سجل تدقيق كامل.

## ADR-015 — التوفر مشتق لا مُدخل
**القرار:** حالة السائق (متاح/مشغول/غير نشط) تُحسب آلياً من حالته الفعلية وليس من إدخال يدوي.
**السبب:** منع التناقض بين حالة السائق وواقعه.
**الأثر:** دقة في التوزيع، لا تحديثات يدوية متعارضة.
